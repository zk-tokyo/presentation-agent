# Verifiable FHE の構成：暗号文評価に「正しさの証明」を添える

<div class="bg-gray-50 rounded-xl border border-gray-200 px-5 py-3 max-w-6xl mx-auto mt-2 text-sm leading-relaxed" style="font-family:'JetBrains Mono',monospace">
<div class="text-gray-800">enc:&nbsp;&nbsp;&nbsp;&nbsp;c &#8592; Enc(pk, x)<span class="text-gray-400 ml-3">// ユーザが暗号化（中身は秘匿）</span></div>
<div class="text-gray-800">eval:&nbsp;&nbsp;&nbsp;c&#39; &#8592; Eval(f, c)<span class="text-gray-400 ml-3">// サーバが暗号文のまま f を評価 (FHE)</span></div>
<div class="text-gray-800">prove&#8321;:&nbsp;&#960;<sub>wf</sub> &#8592; ZKProve&#123; &#8707; x,r : c=Enc(pk,x;r) &#8743; noise 範囲内 &#125;<span class="text-gray-400 ml-3">// ユーザ。x を隠す → ZK 必須</span></div>
<div class="text-gray-800">prove&#8322;:&nbsp;&#960;<sub>eval</sub> &#8592; Prove&#123; c&#39; = Eval(f, c) &#125;<span class="text-gray-400 ml-3">// サーバ。秘密なし → succinct で十分</span></div>
<div class="text-gray-900 font-bold mt-1">verify:&nbsp;Dec(sk, c&#39;) = f(x)&nbsp;&nbsp;かつ&nbsp;&nbsp;Verify(&#960;<sub>wf</sub>, &#960;<sub>eval</sub>) = &#8868;<span class="text-gray-400 ml-3 font-normal">// 機密性 + 正しさ を同時に</span></div>
</div>

<div class="grid grid-cols-3 gap-4 max-w-6xl mx-auto mt-4">
<div class="p-4 bg-white rounded-xl border border-gray-200 shadow-sm">
<div class="text-md font-black text-gray-900 mb-2">FHE が守る範囲</div>
<div class="text-sm text-gray-700 leading-relaxed"><strong>データ機密のみ</strong>。サーバが正しい f を正しく評価したかは無保証 —— garbage を返されてもユーザは気づけない。</div>
</div>
<div class="p-4 bg-white rounded-xl border border-gray-200 shadow-sm">
<div class="text-md font-black text-gray-900 mb-2">証明が埋める穴</div>
<div class="text-sm text-gray-700 leading-relaxed">サーバは「c に f を正しく評価し c&#39; を得た」を証明。ユーザは暗号文の <strong>well-formedness（noise が範囲内）</strong>を証明する。<strong>証明者が違う</strong>点が要。</div>
</div>
<div class="p-4 bg-amber-50 rounded-xl border border-amber-200">
<div class="text-md font-black text-gray-900 mb-2">コスト</div>
<div class="text-sm text-gray-700 leading-relaxed">FHE の <strong>bootstrapping</strong> と ZK 証明生成が支配的で重いのが課題。回路バグは soundness を壊すので検証が要。</div>
</div>
</div>

<div class="mt-4 p-3 bg-gray-50 rounded-xl border border-gray-200 max-w-6xl mx-auto text-sm text-gray-800">
<span class="text-amber-600 font-black mr-1">&#9654;</span>要点：<strong>FHE = 機密性 / 証明 = 正しさ</strong> を分解し、両方要るなら合成する。GW① の「暗号文のまま AI 診断」の模範解がこれ。
<div class="mt-1.5 text-[13px] text-gray-600 leading-snug"><span class="text-amber-600 font-black mr-1">&#9654;</span>注：&#960;<sub>eval</sub> に <strong>zero-knowledge 性は必須ではない</strong>（c, c&#39;, f は公開で隠す witness が無い）。本質は <strong>succinctness</strong> —— 再実行より安く検証できること。SNARK / STARK で十分。ZK が要るのは &#960;<sub>wf</sub>（平文 x を隠す）と、サーバがモデル重み等を秘匿する場合。</div>
</div>

Speaker Notes:
Verifiable FHE 深掘り 2/2 = 構成（前ページのアニメ 4 phase を数式で裏打ち）。
【流れ】① ユーザは pk で平文 x を暗号化し c=Enc(pk,x) をサーバへ。サーバには中身が見えない。② サーバは暗号文のまま関数 f を準同型評価し c'=Eval(f,c) を得る（FHE）。③ ここで問題：サーバが本当に f を正しく評価したか、別の関数や garbage を返していないかは FHE 単体では保証されない。そこで証明を添える。④ ユーザは sk で復号して f(x) を得つつ、証明を検証して「正しさ」も確認する。
【証明は 2 つあり、証明者が違う】ここは講義で必ず分けて話す。(a) π_wf は「c が正規の暗号文で noise が範囲内」の証明。証明者は暗号化した本人（ユーザ）で、witness は平文 x と暗号化乱数 r。これが漏れたら FHE の意味が消えるので zero-knowledge 性が必須。(b) π_eval は「c' = Eval(f, c)」の証明。証明者はサーバで、c も c' も f も公開されているため隠すべき witness が存在しない。
【ZK 性は必要か】レビュー指摘のとおり、π_eval に zero-knowledge 性は本質的に不要。必要なのは succinctness ——「サーバの計算を検証者が再実行するより安く検証できる」こと。したがって SNARK / STARK（succinct argument）で十分で、zero-knowledge は要件に入らない。例外は、サーバ側にも秘密がある場合（モデル重み・独自アルゴリズム f を伏せたまま「正しく評価した」と示したい）で、このときは π_eval も ZK にする。文献名や p8 の合成表で「ZK + FHE」と呼ぶのは通称であり、π_wf が実際に ZK であるため誤りではないが、「Verifiable FHE の本質は zero-knowledge ではなく succinctness」と一度明言しておく。
【なぜ必要か】CLAUDE.md §9 のとおり FHE の信頼前提は「データ機密のみ。計算正しさは別途（Verifiable FHE）」。FHE はサーバにデータを見せないが、正しい計算を強制しない。Verifiable FHE は ZK でその穴を埋める = 「委託 + 正しさ」。
【実装】先行実装は BFV/BGV 暗号文の well-formedness、特に noise が許容範囲内であることを ZK で証明する。c が壊れた暗号文だと復号が破綻するため well-formedness は重要。
【コスト】FHE の bootstrapping（noise リフレッシュ）と ZK の証明生成がどちらも重く、合成すると支配的コストに。回路にバグがあると soundness が崩れる（誤った計算でも π が通る）ので回路検証が要。
【設計の語彙】GW① の「暗号文のまま AI 診断 + 本人が正しさを確認」の模範解がまさに Verifiable FHE。FHE=機密性 / ZK=正しさ を分解し、両方要るなら合成する、という設計フローの実例。
