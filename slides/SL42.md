# ZK 証明をブロックチェーンで公開検証する：Solidity Verifier

<div class="text-sm text-gray-500 mt-1 mb-4">Tornado Cash で見た「コントラクトが <strong>π</strong> を検証」の仕組みを一般化する。<strong class="text-amber-700">Solidity verifier</strong> が ZK アプリとブロックチェーンの橋になる。</div>

Speaker Notes:
Tornado Cash 深掘りの直後に置き、「コントラクトが π を検証」の一般論へ引き上げる。
【Tornado Cash との接続】SL12-13 で見た Tornado Cash のコントラクトは Solidity verifier の実例。預入時に commitment C = H(k, r) を Merkle tree に追記し、引出時に zk-SNARK π（Merkle membership + nullifier）をコントラクトが検証して 1 ETH を払い出す。この「proof をコントラクトが検証 → 状態遷移」のパターンを一般化する。
【Solidity verifier とは】ZK 証明システム（Groth16 / PLONK / STARK 等）の検証アルゴリズムを Solidity で実装したコントラクト。proof π と public inputs を受け取り、on-chain で verify(π, public_inputs) を実行。結果が ✓ なら状態遷移をトリガー（払出・認証・集約など）。証明システムごとに verifier の規模と gas cost が異なるが、詳細は後のスライドで扱う。
【verifier はどこから来るか】Verifier.sol は人間が手書きしない。開発者が書くのは回路定義だけ — circom で `circuit.circom` を書く → `circom` でコンパイルして R1CS 制約系 (.r1cs) と witness generator (.wasm) を得る → snarkjs で trusted setup（Powers of Tau + circuit-specific phase 2）を実行し proving key / verification key を含む `circuit.zkey` を生成 → `snarkjs zkey export solidityverifier circuit.zkey Verifier.sol` で検証鍵を定数として埋め込んだ Solidity コントラクトが出力される。中身は BN254 上のペアリング演算（Groth16 なら e(A,B) = e(α,β)·e(L,γ)·e(C,δ) のチェック）で、EVM の precompile (0x06/0x07/0x08) を叩くだけの数十行。回路を変えれば verification key が変わるので、Verifier.sol も作り直しになる（= 回路ごとに専用 verifier）。
【他のツールチェーン】この「回路/プログラムを書く → verifier を機械生成する」構造は circom+snarkjs 固有ではない。Noir (barretenberg)、halo2 / PLONK 系、SP1・RISC Zero といった zkVM も、それぞれ verifier コントラクトを生成・配布する仕組みを持つ。証明システムごとに verifier の規模と gas cost が違う点だけ押さえる。
【パブリックベリファイアビリティ】ブロックチェーンの本質的価値 = 誰でも検証できる公開台帤。中央の信頼者（trusted verifier）を置かず、全ノードが同じ verifier コントラクトを独立に実行。proof の正しさが「ある権威者の主張」ではなく「合意形成された事実」になる。ZK の verify が単なる数学的検証から、社会規模の信頼基盤へ昇格する。これが「ZKアプリ + ブロックチェーン」の核心的意義。
【設計の含意】ZK アプリを設計する際「proof を誰が・どこで検証するか」は「どの primitive を使うか」と同じくらい重要。オンチェーン検証は gas cost という実コストが伴うため、proof aggregation / recursion で検証コストを圧縮する手法が実務上重要になる（詳細は実装パートで扱う）。
