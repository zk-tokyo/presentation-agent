# グループワーク①：暗号文のまま AI 診断を設計する

<div class="p-5 bg-amber-50 rounded-xl border border-amber-200 max-w-6xl mx-auto mt-2">
<div class="text-amber-700 font-black mb-1">お題</div>
<div class="text-sm text-gray-800 leading-relaxed">ユーザが自分の<strong>医療データ</strong>をクラウドの AI に診断させたい。クラウドにも第三者にも<strong>生データを見せたくない</strong>。さらに「<strong>診断が正しく計算された</strong>」ことを本人が確認したい。— この要件を満たすスタックを設計せよ。</div>
</div>

<div class="p-5 bg-white rounded-xl border border-gray-200 shadow-sm max-w-6xl mx-auto mt-5">
<div class="font-black text-gray-900 mb-2">進め方</div>
<div class="space-y-1.5 text-sm text-gray-700">
<div class="flex items-start gap-2"><span class="text-amber-500 font-black mt-0.5">1</span><span>要件を言語化（アクター / 秘匿入力 / 公開出力 / 信頼境界）</span></div>
<div class="flex items-start gap-2"><span class="text-amber-500 font-black mt-0.5">2</span><span>各 primitive が何を保証するかを思い出し、要件を満たす組み合わせを自分で選ぶ</span></div>
<div class="flex items-start gap-2"><span class="text-amber-500 font-black mt-0.5">3</span><span><strong>ユーザーフローを書き出す</strong>（誰が→何を→どの primitive を通り→<strong>境界を越えるのは何か</strong>を時系列で）</span></div>
<div class="flex items-start gap-2"><span class="text-amber-500 font-black mt-0.5">4</span><span>落とし穴を 1 つ（性能 / soundness / メタデータ / 規制）</span></div>
</div>
</div>

<div class="mt-5 p-3 bg-green-50 rounded-xl border border-green-200 max-w-6xl mx-auto text-center text-sm text-gray-800">
<span class="text-green-700 font-black mr-1">&#10003;</span>発表（各 1 分）：<strong>ユーザーフロー</strong>を見比べ、<strong>「なぜ Verifiable FHE / なぜ MPC / なぜ TEE」</strong>を 1 文で説明できるか
</div>

Speaker Notes:
ホワイトボードのグループワーク（横断比較方式）。全チーム同じお題「暗号文のまま AI 診断」を設計し、最後に設計を見比べる。
【狙い】要件 → 4項目の言語化 → 各 primitive の保証内容を思い出して直接選ぶ → ユーザーフローを書き出す → 落とし穴、という流れを実際に回す。設計フローチャートの決定木を機械的に辿るのではなく、primitive の性質 (何を保証し何を保証しないか) を自分の言葉で適用できるかを問う。成果物はホワイトボード上のユーザーフロー図: アクターを左右に並べ、データ/暗号文/証明がどの primitive を通ってどこで信頼境界を越えるかを矢印で描かせる (SL38 の POD2 フロー図がお手本)。
【模範解の方向性（運営用、配ってよい）】
- Secret Inputs = 患者の医療データ / Public Outputs = 診断結果（本人のみ）/ Actors = ユーザ・クラウド AI / Trust Boundary = クラウドを信頼しない。
- 素朴解: FHE で暗号文のまま推論 → データ機密は守れる。だが「クラウドが正しいモデルで正しく計算したか」は保証されない（FHE はデータ機密のみ）。
- そこで Verifiable FHE = ZK + FHE：クラウドが「暗号文 c に対し正しく f を評価した」ことの証明 π を付ける。本人は復号 + π 検証で「正しさ」も得る。
- 代替案の比較: MPC（モデル保有者とユーザで分散計算、ただしモデルを秘匿したいか/通信コスト）/ TEE（速いが信頼前提がハード・サイドチャネル）。各案の trust 前提とコストを 1 文で。
- 落とし穴: 性能（FHE の bootstrapping が支配的）/ soundness（Verifiable FHE の回路バグ）/ メタデータ（誰がいつ診断したかは隠れない）/ 規制（医療データ = GDPR/HIPAA）。
