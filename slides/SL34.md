# グループワーク②：exploit を渡さず「脆弱性の存在」を証明する

<div class="p-5 bg-amber-50 rounded-xl border border-amber-200 max-w-6xl mx-auto mt-2">
<div class="text-amber-700 font-black mb-1">お題</div>
<div class="text-sm text-gray-800 leading-relaxed">あるセキュリティ研究者が、広く使われるプログラム <strong>P</strong> に深刻な脆弱性（クラッシュ / 任意コード実行）を見つけた。ベンダーに「<strong>確かに動く exploit を持っている</strong>」と示して報奨金を得たい。だが exploit 入力をそのまま渡すと、<strong>パッチ前に盗用・悪用</strong>される恐れがある。<strong>exploit 入力を秘匿したまま「P を破る入力が存在する」</strong>ことを検証させたい。— <strong>zkVM</strong> でこのスタックを設計せよ。</div>
</div>

<div class="flex items-start gap-2"><span class="text-amber-500 font-black mt-0.5">1</span><span>5 要素を言語化（<strong>Secret = exploit 入力</strong> / <strong>Public = P と「破れる」という主張</strong>）</span></div>
<div class="flex items-start gap-2"><span class="text-amber-500 font-black mt-0.5">2</span><span>zkVM の guest は何を実行する？（P を入力 x で走らせ、<strong>脆弱な状態に到達</strong>したことを判定）</span></div>
<div class="flex items-start gap-2"><span class="text-amber-500 font-black mt-0.5">3</span><span>「なぜ zkVM か（入力を見せず任意のプログラム実行を証明）」を <strong>1 文</strong>で</span></div>

<div class="flex items-start gap-2"><span class="text-amber-500 mt-0.5">&#9654;</span><span>検証者は最終的に何を信じる？（zkVM の健全性 + P の同一性 + bug 述語の正しさ）</span></div>

Speaker Notes:
ホワイトボードのグループワーク②（zkVM テーマ）= Proof of Exploit。GW① が「データを隠す(FHE)= 機密性」だったのに対し、GW② は「秘密の入力が性質を満たすことを、入力を見せずに証明する」= zkVM ならではの設計。責任ある開示(脆弱性を盗用させずに存在だけ示す)が動機。
【模範解の方向性（運営用）】
- 5 要素: Actors = 研究者(prover)・ベンダー(verifier)。Secret Inputs = exploit 入力 x。Public Outputs = プログラム P(または P のハッシュ)と「∃x: P(x) が脆弱状態に到達」という述語。Trust Boundary = x は誰にも見せない、proof が存在を保証。
- guest プログラム: P を入力 x で実行し、(a) クラッシュ/assert 失敗/メモリ安全違反など「脆弱状態」に到達したことを検出 → その実行を zkVM が証明。RISC-V 系 zkVM なら P の実バイナリをほぼそのまま guest にできる。

- 設計の肝/落とし穴: (1) prover コスト(P の実行をトレース化するのは重い → precompile/continuations/再帰)。(2) P の同一性: 証明した P が「実際に配布中のバイナリ」と一致することを binding(ハッシュ公開)しないと無意味。(3) ★「脆弱」をどう厳密に定義するか = bug 述語の設計。緩いと別物を脆弱と偽れる(garbage in→ 正しい proof でも主張は空虚)。= zkVM は「P が正しく実行された」しか保証しない。信頼は暗号から「P の同一性 + bug 述語の正しさ」へ再配分される。
【対比の締め】GW①(FHE)=機密性 ／ GW②(zkVM)=「秘密の入力の性質を見せずに証明」。共通教訓: ZK は信頼を消さず再配分する — 何を信じることになるかを設計時に言語化せよ。
