<div class="text-sm font-black text-gray-900 mb-1"><span class="text-amber-600 font-black mr-1">&#9654;</span>なぜ署名するのか</div>
<div class="text-sm text-gray-700 leading-snug">各 validator は毎スロット、ブロックに署名して合意を形成する。量子計算機が現行の <strong>BLS 署名</strong>（楕円曲線）を破るため、ハッシュベースの耐量子署名 <strong>leanXMSS</strong> への置換が必須。</div>
</div>

<div class="text-sm font-black text-gray-900 mb-1"><span class="text-amber-600 font-black mr-1">&#9654;</span>なぜ zkVM が要るのか</div>
<div class="text-sm text-gray-700 leading-snug">leanXMSS は 1 個 <strong>~3,000 B</strong> で、BLS のように単純加算で集約できない。数万 validator 分を毎スロット検証するのは非現実的 → zkVM が全署名の検証を <strong>1 つの小さな proof</strong> に再帰集約する。</div>
</div>

<div class="p-3 bg-amber-50 rounded-xl border border-amber-200">

<div class="text-[13px] text-gray-700 leading-snug"><strong>&#9312;</strong> 対象が違う &#8212; zkEVM は<strong>実行層</strong>、要るのは<strong>合意層</strong>の署名集約。<br/><strong>&#9313;</strong> zkEVM は楕円曲線依存で<strong>量子脆弱</strong>。PQC 移行の VM がそれでは本末転倒。<br/><strong>&#9314;</strong> 速度と<strong>形式検証</strong>のため ISA は最小。</div>

Speaker Notes:
アプリ紹介（証明・検証系）の深掘り 2 = zkVM の応用。LeanVM は「署名集約専用の最小 zkVM」。図は 3 phase で morph する。
【物語】① 多数の leanXMSS 署名（各 ~3,000 B、BLS は 96 B）→ ② LeanVM で再帰的に集約 → ③ 1 つの小さな proof（約 250x 圧縮）。
【背景】量子計算機(Shor)は楕円曲線(BLS12-381)を破るので、Ethereum はハッシュベースの耐量子署名 leanXMSS(XMSS 系)へ移行する。ハッシュベースはハッシュ関数の安全性だけに依存するので量子耐性。
【課題】leanXMSS の署名は約 3,000 バイトと巨大。数万 validator 分を毎スロット扱うには集約が必須。
【なぜ zkEVM ではないのか】受講者の一番の疑問になる点。4 つに分解して説明する。
 (1) レイヤーが違う — zkEVM は execution layer の「EVM の状態遷移が正しい」ことを証明する道具。LeanVM が証明したいのは consensus layer の「数万の validator 署名が正しく検証された」こと。証明対象に EVM の意味論は一切登場しないので、zkEVM を持ち出す必然性がそもそもない。
 (2) 耐量子要件 — これが決定打。主流の zkEVM スタックは BN254 上の KZG / Groth16 / PLONK といった楕円曲線ベースの証明系に依存しており、Shor のアルゴリズムで破られる。PQC 移行のために署名を leanXMSS へ替えるのに、その集約を量子脆弱な証明系でやったら移行の意味が消える。だから証明系まで含めてハッシュベース（Poseidon2 + WHIR / FRI）で閉じる必要がある。
 (3) スロット時間の制約 — 合意は毎スロット回る。汎用 zkEVM の prover コストではスロット内に収まらない。4 命令 + Poseidon precompile + read-only メモリという最小 ISA にして、証明対象を XMSS 検証だけに絞ることで初めて成立する。
 (4) 形式検証 — 合意層クリティカルなコードなので仕様が小さいことに価値がある。EVM 意味論は巨大で形式検証が現実的でない。leanSpec で書き切れる規模に保つ設計判断。
構成は次々ページ。
【位置づけ】Lean Consensus 2026 plan の中核。leanXMSS(署名) / leanSig(Rust) / leanMultisig(=LeanVM, 集約) / leanSpec(Python 仕様)、約 10 client が実装中。zkVM が「汎用」から「用途特化の最小 VM」へ展開する好例。
